Design spec — v1

bradley-os

A single-user web app that replaces three browser tabs — mail, calendar, notes — with one daily-driver: what's unread, what's next, what you were thinking.

Owner: brwang48198@gmail.com Status: Approved for build Drafted: 2026-08-15
Scope

What v1 actually does

Six surfaces, one app. Everything here is either explicitly what you asked for, or the single addition that turned three separate views into something that actually gets used daily.

Today
Home screen on login: unread digest, today's/this week's events, pinned notes, and open todos in one place. new — closes the loop
Inbox digest
Read-only list of unread mail in Gmail's Primary category from the last 24 hours — sender, subject, snippet. No reply, no archive, no mail actions. Signal, not a mail client.
Calendar
Week view backed by Google Calendar. Click-drag to create a block, drag the edge to resize, current-time line. bradley-os authors events; Google Calendar stays the only source of truth.
Notes
Persistent, structured notes (rich text, not plain text) with full-text search. Diagrams embed inline as a block inside a note, or stand alone.
Diagrams
Freeform Excalidraw canvases for architecture sketches and plans — hand-drawn aesthetic, not a corporate flowchart tool.
Todos
A flat checklist — add, check, delete. No projects, no priorities, no due dates. new — smallest possible connective tissue
Architecture

How it's built

Optimized for one person maintaining this for years, with an AI assistant re-deriving context each session — fewer moving parts wins over architectural purity every time.

runtime
Next.js (App Router) + TypeScript, one deployable appRoute Handlers and Server Actions carry the backend — no separate API service, no CORS.
styling
Tailwind CSS + Base UIHeadless primitives copied into the repo (the shadcn pattern) — every visual token is ours, nothing inherited from a default theme.
data
Turso (hosted libSQL/SQLite) via Drizzle ORMVercel functions have no durable local disk; Turso keeps "it's still just SQLite" true while being serverless-safe.
auth
Auth.js, Google provider, single-email allowlistThe sign-in callback rejects every email but OWNER_EMAIL. Login and the Calendar OAuth grant share one consent screen.
calendar
Google Calendar API (googleapis), read/write proxyNo local copy of events, ever — bradley-os never becomes a second source of truth that drifts from what your phone shows.
email
Gmail via IMAP (imapflow) + a Google App PasswordNot the Gmail REST API — see Risks. SEARCH UNSEEN SINCE against INBOX, pulled on load.
calendar ui
FullCalendar — timeGrid + interaction pluginThe only one of three compared libraries with free, out-of-the-box drag-to-create and drag-to-resize.
diagrams
Excalidraw (@excalidraw/excalidraw)MIT-licensed, free to embed forever. tldraw's SDK requires a paid license past a 100-day trial — not a real option for this.
notes editor
Tiptap (ProseMirror, headless)Structured enough to embed a diagram or a calendar-event reference as an inline block, not just flat text.
state
Zustand or JotaiLightweight client state — one user, no cross-client sync complexity to design around.
hosting
Vercel (app) + Turso (data)No volumes, no backup jobs, no container builds — the entire ops surface is a handful of environment variables.

Data model

notes       (id, title, body_json, created_at, updated_at)
diagrams    (id, title, scene_json, note_id → notes.id, nullable, created_at, updated_at)
todos       (id, text, done, created_at, completed_at)

— calendar events are not stored here; Google Calendar is the system of record.

Secrets

GOOGLE_CLIENT_ID · GOOGLE_CLIENT_SECRET · AUTH_SECRET · OWNER_EMAIL · GMAIL_APP_PASSWORD · TURSO_DATABASE_URL · TURSO_AUTH_TOKEN — six values, no vault needed at this scale, just never commit them.

Design system

What it should feel like

The failure mode to design away from: default shadcn purple, Inter everywhere, glass cards on a gradient. The target is closer to Linear's restraint for the scanning surfaces and iA Writer's quiet for the writing surface — because those are genuinely two different cognitive modes, not one template stretched over three features.

Starting palette

Paper#F7F5F1
Ink (dark bg)#0E0E10
Text (light)#1A1A18
Accent — amber#9C6A0E
Hairline border#DEDAD1

One accent, used only for state — unread, today, active — never decoration. No gradients; depth comes from a 1px hairline, never a soft shadow. Deliberately not indigo/violet (the default-feeling post-shadcn accent) and not pure white or pure black.

Type system

UI chrome — Geist Sans / General Sans
Today · 3 unread · 2 events
Notes — Newsreader / Charter
The notes surface should read like a page, not a panel — no toolbar competing with the words.
Metadata — IBM Plex Mono / JetBrains Mono
14:00–15:30 · 2 events · ⌘K

No Inter. UI chrome gets a grotesk with more character; the notes editor switches to a serif built for reading — that switch alone is what makes the notes surface feel authored rather than templated. Mono is reserved for anything that's actually data: timestamps, durations, counts, shortcut hints.

Layout

Persistent left rail — Today / Inbox / Calendar / Notes / Todos — with a single main panel that swaps per section, plus ⌘K as a secondary accelerant for quick-capture, not the primary way to navigate. Inbox and Calendar share one dense, scanning density (compact rows, 8–12px padding); Notes deliberately breaks from it — wider margins, longer line-height — so the shift in density itself signals "this is the slow surface," without a label saying so.

What makes it feel hand-designed

  • Empty states have a voice."No unread mail. Go outside." — not a stock illustration and "Nothing here yet!"
  • Keyboard-native, visibly.Every actionable row shows its shortcut on hover — this is a tool one person uses via keyboard, daily.
  • Motion is functional, not decorative.120–150ms linear-ease on state changes only (checking a todo, completing a block) — never spring-everything.
  • No soft shadows.A 1px hairline border does the work a blurred drop-shadow would otherwise fake.
Risks

Where the estimate is fragile

Four places where the feature as described is more work — or more brittle — than it sounds, flagged so none of them are a surprise mid-build.

Time-blocking is the largest single UI build.

FullCalendar's interaction plugin removes the "build a drag engine from scratch" problem, but reconciling optimistic local state against real Calendar API writes — latency, edits made from a phone mid-session — and always trusting Calendar's own RFC3339 timestamps over manual UTC math still takes real care.

Excalidraw is turnkey, embedding it isn't free.

Mounting it headlessly, debounced save-on-change into scene_json, and correctly restoring a scene's embedded-image files map on load are each small but real integration steps.

Calendar tokens still expire weekly in Testing mode.

Calendar is a "sensitive," not "restricted," scope — cheaper than Gmail's problem, but Testing-mode refresh tokens still expire every 7 days. Tolerable early with a manual re-consent; worth the one-time free verification review once the app is stable.

SQLite wants one process; Vercel gives you many.

A plain local .sqlite file assumes a single long-lived process. Turso's client-server libSQL is specified instead of a raw file specifically to avoid that mismatch under serverless concurrency.

Roadmap

Build order

Real sequence — each phase depends on the one before it existing.

v0

Something end-to-end, fast

— get every surface loading real data before polishing any of them
  1. Auth — sign in with Google, single-email allowlist.
  2. Inbox digest — IMAP fetch, Primary unread/24h list, no styling polish.
  3. Calendar — read Google Calendar, list view only, no drag yet.
  4. Notes — flat list + Tiptap editor, no diagrams yet.
  5. Todos — flat checklist.

This document's scope

  1. Today dashboard — unify all four surfaces into one home screen.
  2. Calendar — drag-to-create / drag-to-resize time-blocking.
  3. Diagrams — Excalidraw, embeddable inline in notes.
  4. Full-text search across notes.
  5. Visual design system applied throughout — palette, type, motion, empty states.
